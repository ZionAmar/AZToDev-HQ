# PROB-2026-09-09-1788961533370 — Recurring "nothing is happening" / stuck feeling: three compounding causes

## Severity guess
SEV2

## Who reported
Founder (ציון), Telegram — "יש פה הרבה התקלויות ושגיאות של טיימאוט, למה זה קורה, תבדקו ותרשמו את זה בבעיות שלכם שזה לא יקרה יותר, תלמדו מזה."

## What broke / what hurts
The founder repeatedly experienced the same symptom — asking "is anyone actually working?" / "why still not uploaded?" — across many turns on the same KidNest GitHub upload task. It is not one bug; today's runs traced it to three compounding causes:

1. **Desk↔GitHub gap.** The ChemiCloud Telegram desk (`aztodev-desk`) has no GitHub auth on the VPS, so it could not `git pull` HQ state written by Cloud runs. Specialist progress (Nadav reports) reached the founder via Telegram but never reached HQ git, so the next Cloud run started blind and re-opened phases that were already resolved (stake-confirm loops, re-scans). Fixed today by `hq/lib/hq-pc-mirror.mjs` — Nadav's PC now mirrors HQ inbox/outbox to the desk when the VPS itself has no GitHub auth. (See commit "Bridge HQ files to ChemiCloud desk via Nadav PC mirror when VPS has no GitHub auth.")
2. **False "done" without verification.** `ops/config/factory.json` (`activeWork`), `ops/intake/kidnest-github-upload-board.json` (KNU-03/KNU-04), and outbox `agents/34-pc-ops/outbox/2026-09-09_knu03-repo-url.md` all recorded the KidNest push as done with a repo URL and a completion timestamp. A live check this session (`gh repo list ZionAmar`, `gh repo view ZionAmar/kidnest`) found **no such repo** — 18 repos exist under the owner, none named kidnest. A plan/intent to fix a blocker (`gh` not authenticated on the PC) was written as if it had already been executed and confirmed. This produced direct contradictions in the same thread: HQ said "done", Noa's live check said "not done."
3. **No single durable thread.** Before `ops/founder-channel/ledger.jsonl` was git-tracked, Cloud runs only saw the gitignored, VM-local Telegram log, which dies with the VM. Every fresh Cloud run re-derived status from scratch instead of continuing, which reads to the founder exactly like a timeout/hang even when work was in fact progressing.

Net effect: no single request literally "timed out" technically — the platform combined stale desk state + an unverified completion claim + a non-persistent thread into something that felt like repeated silent failures.

## Impact
- Founder trust erosion, repeated identical status questions across many turns.
- Wasted Linear ticket churn (EMET-153/154 closed then found to be false; had to be re-verified).
- Time lost to the founder having to escalate the same issue multiple times before it got fixed.

## Fix status
- Ledger persistence: done (`ops/founder-channel/ledger.jsonl`, git-tracked, read before every Cloud turn).
- Desk↔GitHub bridge for a VPS with no GitHub auth: done (`hq/lib/hq-pc-mirror.mjs`).
- KidNest false-done: caught and folded into `pc-production-inventory` (PCI-02) for a real re-verification pass instead of a silent repeat.

## Prevention rule (apply going forward — binding for every agent)
1. **No task that produces an external artifact (GitHub repo, pushed commit, Linear issue, uploaded file, sent email) may be marked `done` without the real, read-only verification output attached to the outbox artifact.** A description of an intended fix is not evidence.
2. Before repeating any "done"/"live" claim about an external system to the founder, spot-check it with a read-only call when feasible — especially when the founder is re-asking "why isn't this done," which is itself a signal the git-tracked state may be stale or wrong.
3. Every specialist update must land in git (ledger + outbox), not only Telegram, before the next Cloud run is trusted to continue from it.
