# PROB-2026-09-09-1788961972584 — Repeated timeouts / disconnects causing loop-backs on multi-step tasks

## Severity guess
SEV2 — no data loss, but repeated founder-visible stalls and duplicate work on the same task (KidNest upload took three restart loops before closing).

## Who reported
ציון (founder), Telegram, 2026-09-09. Quote: "יש פה הרבה הנתקות ושגיאות של טיימאוט, למה זה קורה — תבדקי ותדאגי שזה לא יקרה יותר".

## What broke / what hurts
Cursor Cloud runs are ephemeral — each run dies when the task/message ends (`_company/COMPANY_LOOP.md`, line 1). Until today, intermediate progress (scan results, "location confirmed", partial PC work) lived only in the live Telegram thread and in `ops/runtime/` (gitignored, wiped every VM). When a run ended — whether from an actual network timeout/disconnect on the PC worker side, or simply the Cloud message ending — the next run had no memory of what was already confirmed, so it re-asked "is the folder right?" and re-ran the scan instead of continuing to upload.

From the founder's side this looked like: "nothing is happening" / "another timeout" every time a Cloud run boundary was crossed, even on turns where no real error occurred.

## Steps to reproduce (if bug)
1. Delegate a multi-step PC task (scan → confirm → create repo → push).
2. Let the Cloud run end after step 1 or 2 (normal end-of-turn, or an actual PC-side timeout).
3. Start a new run/turn on the same task.
4. Observe: new run re-asks for folder confirmation / re-scans instead of resuming at the next open task.

## Impact
- KidNest GitHub upload (KNU-01..04) needed 3 restart loops across ~4 hours before closing (see `agents/00-ceo/memory/learning-log.md`, 2026-09-09 entries).
- Founder had to repeat the same status question multiple times ("מישהו עובד עכשיו?").
- Erodes trust that the factory "remembers" work between runs.

## Root cause
Not a single bug — a structural gap: no git-tracked, single-source-of-truth ledger of (a) what a specialist already confirmed and (b) what step is next, checked **before** re-asking or re-scanning.

## Fix already applied today (evidence)
- `ops/founder-channel/ledger.jsonl` — git-tracked Telegram ledger, read before every Cloud turn (commit `c22bbef`).
- `ops/intake/kidnest-github-upload-board.json` — per-task status with `completedAt` / `artifact` fields, so "done" is a file, not a memory.
- `ops/config/factory.json` → `activeWork` — single WIP=1 pointer with `waitingFor` that must never be blank while a task is open.

## Prevention rule (new — added to `_company/handbook/failure-handling.md` and `_company/COMPANY_LOOP.md` in this same change)
1. **Persist immediately, not at the end.** Every specialist writes its board/outbox/ledger update the moment a sub-step closes — before ending the turn — because the run can be cut at any point after that.
2. **Read-before-ask.** Before requesting confirmation or re-running a scan, check `ledger.jsonl` + the task board for that step. If it is already marked done/confirmed there, skip straight to the next open step.
3. **3-strikes stop.** If the same step needs to be re-confirmed a 3rd time across runs, stop delegating it silently — flag it to Noa as a process failure, not a retry.

## Related initiative / product
KidNest GitHub upload (`ops/intake/kidnest-github-upload-board.json`), applies to all future `34-pc-ops` multi-step delegations.
